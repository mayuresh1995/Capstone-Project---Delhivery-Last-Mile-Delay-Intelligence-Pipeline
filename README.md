# Delhivery Last-Mile Delay Intelligence Pipeline

This repository contains an end-to-end data pipeline built on synthetic shipment data to estimate delivery hours, flag parcels at high risk of delay, and cluster operational hubs into distinct segments. The final output is an automated scoring script that merges parcel-level risk probabilities with hub-level operational profiles to generate a prioritized action queue.

## How to run

To reproduce the pipeline, run the scripts from the repository root in the exact order below. Each step relies on files generated by the preceding script.

```text
python -m pip install -r requirements.txt
python generate_data.py
python -c "from pathlib import Path; Path('outputs').mkdir(exist_ok=True)"
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

generate_data.py: Generates raw hubs, historical shipments, and new shipment data (data/new_shipments.csv).
part_a_clean_eda.py: Cleans the raw data and outputs data/modelling_table.csv along with EDA summary tables and correlations.
part_b_regression.py & part_c_classification.py: Train and evaluate the core predictive models, saving metrics under outputs/.
part_d_segments.py: Runs K-Means clustering on the hubs.
package_model.py: Bundles the production artifacts into models/delay_model.pkl, including threshold, feature-order, and imputation sidecars.
predict_delay.py: Consumes the packaged model and hub segments to score new shipments into outputs/new_shipment_actions.csv.

Environment Dependencies: Python libraries are pinned in requirements.txt (pandas==3.0.3, numpy==2.5.0, scikit-learn==1.9.1, joblib==1.6.0).

## Data findings

- The raw export of 1,224 shipments required cleaning down to 1,200 valid rows by dropping 24 duplicates. We addressed missing data points (36 distances, 24 parcel weights, 12 declared values, and 18 payment modes). Five weights crossed the anomaly cutoff and were treated as nulls, while service-type spellings were normalized from 12 messy variants down to 3 standard categories.
- Continuous features were imputed using the cleaning medians: 314.95 km for distance, 1.83 kg for parcel weight, and INR 1,121.50 for declared value. Following cleaning, the modeling table was completely free of nulls in both features and target variables.
- Across the dataset, we observed 278 delayed shipments (23.17% overall delay rate).
    By Service: Economy (8.57%), Standard (20.56%), Express (48.97%).
    By Hub Tier: Tier 1 (4.00%), Tier 2 (21.50%), Tier 3 (44.00%).
    By Distance Band: Ranged sharply from 2.19% for trips under 200 km up to 85.23% for distances exceeding 601 km.
- Delivery hours correlated most strongly with promised hours (0.8372), distance (0.4013), and total stop count (0.3247). Keep in mind these are descriptive associations in synthetic data, not proven causal drivers.
- Declared value exhibited a right-skewed distribution (mean of INR 1,533.05 vs. median of INR 1,121.50), which was smoothed via a natural-log transformation for modeling.

## Model results (regression)

- A naive training-mean baseline resulted in a validation RMSE of 18.855 hours (R^2 = -0.0212). Among candidate architectures, a standard Linear Regression edged out gradient boosting with the lowest validation RMSE of 4.891 hours (vs. 4.917 for Gradient Boosting, 5.468 for Random Forest, and 6.280 for Decision Tree).
- Decision tree depth was optimized at 6 (validation RMSE 6.280), and gradient boosting settled on a learning rate of 0.1.
- Because Linear Regression achieved the lowest validation RMSE, it was selected for production. It delivered robust cross-validation performance (R^2 = 0.9261, with Gradient Boosting at 0.9352) and generalized strongly to the held-out test set with an RMSE of 4.524 hours and an R^2 of 0.949.

## Model results (classification)

- A naive "all on-time" classifier yielded 76.67% accuracy but an F1 score of 0, completely missing all 42 delayed parcels in the validation split. By contrast, Logistic Regression achieved an F1 of 0.8046, beating out the tuned decision tree (0.7470) and default random forest (0.7848).
- Feature selection via F-scores highlighted distance, hub tier, hub daily capacity, stop count, promised hours, rain flags, and sale-event flags as the top 7 predictors. All five noise/bookkeeping columns ranked outside the top 7 and had F-scores under 10 (contributing a combined random-forest importance of 0.2244).
- Testing various SelectK thresholds proved that restricting the model to the top 7 features yielded the highest validation F1 score (0.8333), outperforming models trained on 5, 10, 12, or 17 features.
- A classification threshold of 0.5 was selected as the highest tested threshold that met the validation recall requirement of at least 0.80. At this threshold, validation precision hit 0.7955 and recall hit 0.8333 (F1: 0.8140). On the unseen test set, the model achieved a precision of 0.6889, recall of 0.7561, and F1 of 0.7209.

## Operations recommendation

- (K=3): Clustering the 24 hubs into 3 operating playbooks yielded clean operational profiles:
    Standard (7 hubs): Avg 47.24 delivery hours, 2.57% delay rate, 188.93 km average haul, 55.37 stops.
    Watch (8 hubs): Avg 56.81 delivery hours, 15.50% delay rate, 314.18 km average haul, 70.72 stops.
    Escalate (9 hubs): Avg 64.65 delivery hours, 46.00% delay rate, 470.48 km average haul, 84.34 stops.
- While evaluating K=4 (ratio = 6.305) and K=5 (ratio = 6.887) marginally increased the across-to-within distance ratio over K=3 (5.393), they produced overly small clusters of 4 and 2 hubs respectively—too granular to sustain independent operational playbooks.
- Four hubs showed mismatches between their structural tier and assigned cluster behavior:
    HUB07 (Kolkata, Tier 1) mapped to Watch.
    HUB13 (Nagpur, Tier 2) and HUB15 (Kochi, Tier 2) mapped to Escalate.
    HUB22 (Dehradun, Tier 3) mapped to Watch.
    Review these specific nodes with ground operations before modifying baseline tier metadata or local routing logic.
- Running the batch scorer across 48 new synthetic parcels flagged 8 at the 0.5 threshold. 6 flagged parcels routed through Escalate hubs were assigned to hub managers for intervention, 2 parcels triggered proactive customer service calls, and the remaining 40 proceeded down standard operational queues.

## Production plan and Limitations

### Production plan

- Swap out synthetic inputs for governed operational streams only after verifying that feature definitions, units, hub mappings, and null-handling logic strictly match production databases.
- Deploy scoring as a scheduled batch job or an inline service. Enforce strict input schema validation, ensure feature alignment against the saved schema, and maintain an audit log of all risk probabilities and generated actions.
- Always couple the model binary, threshold, feature order, and training imputation medians together. Test candidate packages on out-of-time historical windows before promoting them to production.
- Continuously track input completeness, score distributions, flagged volumes per hub segment, and ground-truth delay outcomes. Set up automated alerts for data degradation or shifts in alert volume before triggering a full model retrain.
- Keep human oversight central for high-risk escalations and customer communications. Use downstream resolution data to evaluate whether automated interventions actually mitigate delays.


### Limitations

- Because all underlying data is simulated, performance metrics do not guarantee identical results on live Delhivery network traffic or real customer behavior.
- The classifier trains on 1,200 historical rows and evaluates on 180 test rows (containing 41 delayed parcels). Real-world noise could cause variance, and the decision threshold was optimized on a single validation split.
- The current validation uses a stratified random split rather than a forward-in-time time-series split, meaning it doesn't fully account for seasonal shifts, macro route changes, or operational drift.
- Hub segments are static K-Means groupings of historical hub averages; they do not prove direct causal drivers or inherently invalidate official hub tier rankings.
- The thresholding logic provides a pragmatic triage mechanism rather than a fully calibrated probability guarantee. It does not measure customer response success rates, intervention capacity limits, or the cost overhead of false positives.
